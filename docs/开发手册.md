## 2. 业务规则（不可违背）

### 2.1 学生住宿：全班统一住校

本班学生全部为住校生，**不存在走读情况**。因此：

- Student 数据模型**不包含** `boarding` 字段（Phase 2.1 已于 2026-09-09 移除并清理全部遗留，见 §9.1）；
- UI **不出现**住宿 / 走读选择；
- 不设计走读学生相关业务。

> `dormitory`（宿舍文本）**保留**：它是「住在哪间宿舍」的中性事实，与住校 / 走读二元状态无关；卡片 / 详情仅在存在宿舍文本时展示「宿舍 · ××」。

### 2.2 周末返家：档案存「事实」，周末模块存「行为」

班主任需要依据学生家庭所在地，快速判断周末返家情况。**两个概念严格分开，不得混淆**：

| 概念           | 归属                     | 内容                                                           |
| -------------- | ------------------------ | -------------------------------------------------------------- |
| 家庭所在地事实 | 学生档案（Student）      | `familyAddress` / `familyLocation`，**静态行政事实**，长期不变 |
| 返家行为       | 周末管理（未来 Phase 7） | 某一个具体周末的**返家申请、审批、离校、返校、统计结果**       |

`familyLocation.scope` 只是家庭所在地的行政区划事实分类：

| 枚举值            | 中文         |
| ----------------- | ------------ |
| `changdu-city`    | 昌都市区     |
| `changdu-county`  | 昌都市其他县 |
| `outside-changdu` | 昌都市外     |

**红线**：

- scope 代表"家庭在哪个行政区域"，**不代表是否允许学生回家**；
- 代码中**永不出现** `canGoHome` 之类的字段，**不允许 AI 或规则从 scope 推导"能否回家"**；
- 是否批准返家属于周末管理模块的行为决策，由未来的周末管理数据承担；
- 学生档案只回答「学生是谁、基本信息、家庭地址在哪里」。

### 2.3 其他已确立规则

- **重名学生区分**：重名（如两名"旦增卓玛"）通过「姓名（学号后四位｜座位号）」识别，如 `旦增卓玛（0101｜1 号）`。展示名统一走 `formatStudentDisplayName()`，任何面向用户的场景（toast、确认框、详情标题、列表 meta）不得裸用 `name`。
- **删除语义**：删除 = 软删除（`deletedAt`），**当前无回收站入口**，对用户表达为「从学生列表中移除，无法撤销」。文案不得暗示"以后可以恢复"。
- **空值展示**：面向用户的空值一律显示占位「—」，不得渲染 `undefined` / `null` 文本。
- **中文文案**：界面文案使用中文，全角标点。

### 2.4 教室与座位：固定真实教室（Phase 3A 确立）

- 教室固定：**高一 9 班**，7 排 × 9 列（分列 3-3-3，左 3｜中 3｜右 3），共 63 座；全班 62 人就座。**第 63 号（末排尾座）留空**：自动就座 / 新建方案不占用，但可手动拖入（全班只有 62 名学生，就座数不会超过 62）；
- 过道固定（三个列块之间各一条）、讲台前方中央、前门右前（右墙）、后门左后（左墙）、窗户在右墙——**不是自由画布**：不允许增删列、移动过道 / 讲台 / 门；
- 修改教室参数的唯一入口是 `src/types/classroom.ts` 的 `ClassroomConfig`（组件与页面一律经 store 读取 `DEFAULT_CLASSROOM_CONFIG`，**不硬编码教室数字**）；
- 座位编号 = 行优先座位号（row-major 1–63），与学生档案 `seatNumber`（1–62）直接对应（§5.1），保持「座位号」原有展示语义；
- 「老师 / 学生视角」只是显示顺序的上下翻转，座位数据与选中态不因视角改变；
- 座位图强调标记（班委 / 高个 / 其他标签）只读学生档案既有字段、仅用于展示，**不写回学生数据**；「高个」目前由「高个」标签表达（档案暂无独立身高字段）；
- 换座只支持两类动作：已就座 ↔ 已就座 = 交换（记 2 条日志）、已就座 → 空位 = 移动（记 1 条）；从空位拖起 / 拖回原位 / 拖到空地均不动作、不记录、不提示（Phase 3B 确立）。换座只改当前方案，**不改学生档案**；多选 / 框选换座属 3D 范围，未实现；
- `SeatChangeLog` 自动记录（Phase 3B 起产生，§9.3）：UUID / ISO / 绑定当前方案 planId / `studentName` 快照；学生名统一「姓名（学号后四位）」`formatStudentShortName`，位置统一「N排M列」`seatPositionShort`；先入会话内「本次调整」，由「保存本次调整（N）」归档进方案 `changeLogs` 并弹摘要（本次调整未保存前不入 localStorage，切换 / 新建方案即清空）；
- 学生被删除 → seat store 自动释放其在**全部**方案中的座位（空位即显示「＋」，不留脏 studentId、不写换座日志、不回溯改写已归档日志）；
- 面向用户的换座提示（toast / 摘要 / 信息卡）用「姓名（学号后四位）」与「第N排第M列」长文案，遵循 §2.3 不裸用姓名的规则。

**自动排座（Phase 3D 确立，§9.5）**

- 输入 = **学生档案既有字段 + 约束表 + 教室配置**，**不新增任何学生字段**（无身高 / 视力 / 纪律）。需求文档中没有排座规则条目，规则语义由 3C 约束类型承载：
  - **硬约束**（`no-deskmate` 不能同桌 / `no-adjacent` 不能相邻）：自动排座**必须满足**，无法满足则不生成方案，改为逐条报告冲突；
  - **软规则**（`back-row` 坐后排 = 第 5–7 排 / `front-row` 坐前排 = 第 1–2 排 / `same-block` 同区块）：**尽量满足**，未满足由约束检查面板 rules 分组逐条提示（判定与消息单一来源）；
  - 「高个」标签派生**低权重**后排偏好（无需录规则）；同一学生既有 `front-row` 规则又带「高个」标签时**显式规则优先**；
- 结果落地 = **生成新方案**（原名「自动排座 N」），原方案原样保留；自动排座**不写换座日志**（它是初始排法而非换座），差异查看走 3C 方案对比；
- 「＋ 新建方案」仍按学生档案 `seatNumber` 生成（**档案座位号与方案座位自 3B 起即脱节，3D 沿用**）；只有「自动排座」使用约束与规则；
- 「换一种排法」= 换种子重排且**沿用同一方案**（不堆积方案）；「撤销」= 只撤销本次自动排座（切回原方案 + 删除该方案），**非通用撤销栈**，状态为页面级、不跨刷新；
- 求解是**确定性**的：同一输入 + 同一种子 = 同一结果（换种子 = 换一种排法）；学生排布顺序在求解器内部计算，不依赖学生表顺序。

### 2.5 工作台：班主任的默认首页（Phase 4 确立）

- 工作台（首页 `/`）是班主任每天打开应用后的**默认首页**，定位为「今天要做什么」：今日课程、今日待办、快捷入口、本周课时统计；**不做大屏仪表盘**（不做图表 / ECharts 风格 / 大面积色块），学校场景以手机为主；
- **手机优先**：375px 起可用，卡片单列、快捷入口两列；PC 自适应（最大宽度约 960px 居中，快捷入口 4 列）；卡片风格与座位管理一致（自研 UI Kit + 松石青主题，§6）；
- **数据就地取真实状态，不臆造业务结论**：课表当前为本地种子数据（`stores/timetable.ts`，只读，无编辑入口），「今日课程」只显示**今天**的课（星期由 `useToday()` 的当前时间解析，跨零点自动切换）；「本周课时」按周课表统计；**「较上周 ——」为占位**——历史周次对比需要保存往周课表，未实现前不显示任何推测值；
- **待办本阶段只支持勾选**（勾选即持久化、刷新保持）；新增 / 删除 / 编辑 / 跨天归档均未实现，界面文案不得暗示这些能力（§11.5）；
- **不新增一级导航、不新增路由**：快捷入口只跳转既有路由，未开放的入口（家校沟通）标注「规划中」并给出提示，不做「点击无反应」的死入口；
- 工作台是**只读消费者**：不修改 Student / SeatPlan / Constraint 三个 store 的数据与语义；课表数据不与学生档案、座位方案互写。

### 3.1 状态管理

进入 Pinia 的有六个 store：

- `stores/app.ts`（`useAppStore`）：全局应用状态——`syncing` / `lastSyncedAt` + 模拟 `sync()`（Phase 0 占位逻辑，由 AppHeader「同步」按钮触发，注释注明"后续接入真实后端"）。
- `stores/student.ts`（`useStudentStore`）：学生领域数据，API 见 §7.2。
- `stores/seat.ts`（`useSeatStore`）：排座领域数据——教室配置（唯一事实来源）+ 座位方案（多方案 / 当前方案 / 方案 CRUD / 换座与日志 / 求解结果落库），职责与 API 见 §9.2–§9.5。
- `stores/constraint.ts`（`useConstraintStore`，Phase 3C）：座位约束（5 类：不能同桌 / 不能相邻 / 坐后排 / 坐前排 / 同区块）CRUD + localStorage 持久化 + 学生删除联动清理，见 §9.4–§9.5。
- `stores/timetable.ts`（`useTimetableStore`，Phase 4）：课表数据（`lessons` / `weekLessonCount` / `lessonsOf(weekday)`）+ localStorage 持久化；**本阶段只读**（无编辑 API），见 §9.6。
- `stores/dashboard.ts`（`useDashboardStore`，Phase 4）：工作台今日待办（`todos` / `toggle(id)`）+ localStorage 持久化；**本阶段只有勾选**（无增删改），派生计数不进 store、由卡片就近计算，见 §9.6。

页面局部状态（搜索词、筛选、视角、弹窗开关、表单）留在组件内，不进入 Pinia。

### 3.2 数据持久化（当前：Pinia → localStorage）

```
Pinia (students ref)
   ↓ deep watch
localStorage ('teacherdesk:students')
   ↓ 启动 load
Pinia (normalizeStudent 升级后回填)
```

- **为什么用 localStorage**：后端尚未接入（CloudBase / PostgreSQL 未开工），本地优先；先让班主任可离线使用，数据模型在真实接入前得到实战打磨。
- **存储键**：`appConfig.storageKeyPrefix + ':students'` → `'teacherdesk:students'`（`src/config/index.ts`）。
- **安全保护（全部已实现，勿回退）**：
  1. 首次启动（键不存在）→ 写入 6 名种子学生并返回；
  2. `JSON.parse` 整体包 `try/catch` → 失败仅告警并返回空列表，不崩溃；
  3. 解析结果经 `Array.isArray` 守卫 → 非数组（外部手工改动等）返回空列表；
  4. 逐条过滤非法元素（`typeof item === 'object'`）后 `normalizeStudent()` 升级；
  5. 持久化写入 `try/catch`（配额耗尽 / 隐私模式不中断应用）；
  6. 全部数组更新为**不可变更新**（spread + 重建数组），由 deep watch 触发写盘。
- **排座键**：`teacherdesk:seatPlans`（同样以 `appConfig.storageKeyPrefix` 拼接，`stores/seat.ts`）保存全部座位方案数组——读写的守卫、try/catch、deep watch、不可变更新与 seed-on-null 策略同 student 完全一致；load 时逐条 `normalizeSeatPlan()` 只信 row/col/studentId，整表重建为与教室配置一致的 63 座，缺座 / 越界不白屏。
- **座位约束键**：`teacherdesk:seatConstraints`（`stores/constraint.ts`，Phase 3C），同款守卫与 deep watch。
- **课表 / 待办键（Phase 4）**：`teacherdesk:timetable:lessons`（`stores/timetable.ts`）与 `teacherdesk:dashboard:todos`（`stores/dashboard.ts`）——键名一律以 `appConfig.storageKeyPrefix` 拼接（§11.3）；读写的 `Array.isArray` 守卫、整体 try/catch、deep watch 写盘、不可变更新与 seed-on-null（无缓存时写入种子课表 / 种子待办）与既有 store 完全一致。两者都在 load 时逐条 normalize：**课表**丢弃星期 / 节次非法（非 1–7 / 非正整数）或科目 / 班级为空的记录并补 id、`location` 空串归 `undefined`；**待办**丢弃文本为空的记录、`done` 非 `true` 一律视为未完成、缺 id 补 id。解析失败或非数组时告警并重置为空（不崩溃、不覆盖其他键）。
- **normalizeStudent 如何升级旧数据**（`src/utils/student.ts`，load 时逐条调用，不引入 migration 框架）：
  - 旧数据无 `familyAddress` → 归一为 `''`；非 string 同样归 `''`；
  - `familyLocation` **整体缺失 → 保留 `undefined`**（展示层显示「—」，不臆造分类）；
  - `familyLocation` 存在但 `scope` 无法识别 → 回退 `'changdu-county'`（本校学生以昌都籍为主）；
  - `prefecture` / `county` 非 string → 归 `''`；
  - Phase 2.1（2026-09-09）起：历史数据中的 `boarding` 遗留键一并剔除（`delete normalized.boarding`），不再随 deep watch 写回持久层；
  - 升级只发生在内存（load 后返回新对象）；首次写操作由 deep watch 自动把升级后的完整数据持久化，**旧数据不会被覆盖丢失**。

```ts
// src/types/timetable.ts —— 课表（工作台「今日课程」「本周课时」的数据源）

  id: string
  weekday: Weekday // 星期（自动识别"今天"由页面层的 weekdayOf(new Date()) 提供）

### 7.2 Store API（`src/stores/student.ts`，返回：全部含软删数据、活跃学生 computed）

| API                                              | 语义                                                  | 返回                     |
| ------------------------------------------------ | ----------------------------------------------------- | ------------------------ |
| `students`                                       | 全部学生（含软删，原始持久化对象）                    | `Ref<Student[]>`         |
| `activeStudents`                                 | 未删除学生 computed                                   | `ComputedRef<Student[]>` |
| `searchStudents(keyword, {gender?, cadreOnly?})` | 搜索 + 筛选，按学号升序                               | `Student[]`              |
| `addStudent(data)`                               | 新增；**学号被占用 → 拒绝写入**                       | `Student \| undefined`   |
| `updateStudent(id, patch)`                       | 更新；**学号被其他学生占用 → 拒绝**（允许保留自己的） | `Student \| undefined`   |
| `removeStudent(id)`                              | 软删除（写 `deletedAt`），仅活跃记录可删              | `boolean`                |

学号唯一性为**双层防御**：表单先提示（`validate()` 排除自身 id），Store 再兜底（拦截绕过表单的写入入口）。调用方必须检查 `undefined` 返回并给用户反馈（`index.vue` 已处理：`新增失败：该学号已存在` / `保存失败：该学生记录不存在`）。

### 9.5 Phase 3D —— 自动排座（约束求解 + 撤销）✅ 已完成（2026-09-10）

Phase 3 拆分见 §9.2。**3A / 3B / 3C / 3D 全部交付，排座模块至此完整。** 规则依据 §2.4。**需求范围由用户 2026-09-10 动手前拍板（四项决策）**：

| 议题     | 结论                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| 规则输入 | **仅用现有数据**（学生档案既有字段 + 约束表），**零学生模型改动**（不加身高 / 视力 / 纪律）                            |
| 约束关系 | `no-deskmate` / `no-adjacent` = **硬约束**；`back-row` / `front-row` / `same-block` 三个 3C 预留规则位**启用**为软规则 |
| 结果落地 | **生成新方案**（原方案原样保留，天然可对比 / 可切回）                                                                  |
| Undo     | **只撤销自动排座**（切回原方案 + 删除新方案），不做通用撤销栈                                                          |

> 背景：需求文档中没有排座规则条目，`Student` 也没有身高 / 视力 / 纪律字段（「高个」仅为自由标签）→ 3D 的实质是**约束求解器**：满足硬约束的前提下尽量满足教师录入的软规则。**不臆造业务规则**（§11.5）。

**求解器（`src/utils/seatArrange.ts`，纯函数，无 store 依赖）**

- `arrangeSeats({ students, constraints, config, seed })`：硬约束**绝不违反**；未能全部满足时返回 `{ ok: false, conflicts }` 且**不产出方案**（冲突逐条为面向用户的文案，已去重，如「不能同桌：旦增卓玛（0918） 与 旦增卓玛（0924）」）；
- 算法：贪心放置（学生按**硬约束度降序 → 学号升序**，候选位按软分择优）+ 换种子重启（上限 200 次）+ 局部搜索（随机交换 / 移入空位，硬约束不破且软分提升才接受，上限 3000 步）；
- 软分权重：手工规则 3 >「高个」标签派生偏好 1；同一学生既有 `front-row` 规则又带「高个」标签 → **显式规则优先**（派生偏好跳过）。检查器的 tall 分组共用同一判定（`explicitRowRuleStudentIds`：有显式坐后排 / 坐前排规则的学生不再报「高个坐前排」），否则求解器按教师规则把高个学生排到前排后，面板会立刻报一条工具自己造出来的警告；
- **确定性**：xorshift32 种子 PRNG（不引依赖），同输入 + 同种子 = 同结果；排序键全部在函数内部计算，**与调用方数组顺序无关**（学生表顺序随持久化 / 重载变化）；
- 输出恒为完整 63 座网格（`buildSeatGrid` 重建，末排尾座留空）；学生 > 62 时按学号升序截断并回报 `unplacedStudentIds`；
- `summarizeArrangeInput()` 供弹窗展示「参与学生 / 可排座位 / 硬约束 / 软规则 / 高个」计数，**与求解共用同一套判定**（停用约束、悬空学生一律不计）；
- 几何判定复用 3C 的 `areDeskmates` / `areAdjacent`（本阶段导出）→ **检查器与排座器的「同桌 / 相邻」语义不漂移**。

**约束语义落地（`src/utils/constraint.ts` / `src/types/constraint.ts`）**

- 共享常量与判定：`HARD_CONSTRAINT_TYPES`（硬）、`isPairConstraintType`（是否需学生 B：不能同桌 / 不能相邻 / 同区块为双人型，坐后排 / 坐前排为单人型）、`BACK_ROW_MIN`（= 5，仅检查器用）、`explicitRowRuleStudentIds`（有显式坐后排 / 坐前排规则的学生，检查器与求解器同源）；
- 检查器新增第 3 类检查 rules 分组：`back-row`（排号 ≥ 5）/ `front-row`（≤ 2）/ `same-block`（同一列块）未满足 → **warn**（只提醒，自动排座尽量满足），消息如「X 应坐后排，当前在第 2 排」「A 与 B 应同区块，当前 左区 / 右区」；未就座者跳过（与关系型一致）；
- 删除 3C 遗留且无引用的 `MANUAL_CONSTRAINT_TYPES`。

**Store（`src/stores/seat.ts`）**

- `createPlanFromSeats(seats, name?)`：**不信任传入数组**——`occupantsFromSeats()` 按行列重算座位号、同一学生只保留序号最小者、末排尾座强制留空，再由 `buildSeatGrid()` 整表重建（恒 63 座，id / block 由行列重算）；置为当前 + 清空「本次调整」；默认名「自动排座 N」（最小不重名序号）；
- `replacePlanSeats(planId, seats)`：供「换一种排法」——**沿用同一方案与方案名**，只替换座位并刷新 `updatedAt`（当前方案时清空待提交记录）；
- 自动排座**不写 changeLogs**（它是初始排法而非换座），差异查看交给 3C 方案对比。

**页面与交互（`src/views/Seats/`）**

- 页头「自动排座」按钮（对比查看时隐藏；无方案 / 无学生时禁用）→ 新增 `SeatArrangeModal.vue`：输入摘要 + 空输入提示 + 超容量警示 + 硬约束冲突列表（红块）+「生成方案」；**弹窗不读写 store**，求解与落库都在页面编排层（成功 / 失败统一提示）；
- 生成成功即落新方案 + toast；**结果条**（主色，与对比提示条同族样式）常驻「已生成「自动排座 N」· 未满足软规则 K 条」（K 取检查器 rules 分组，口径与面板一致）＋「换一种排法」（换种子重排，**沿用同一方案不堆积**）＋「撤销」＋「关闭」；
- 落库前清空 `selectedSeatId` / 点击换座模式 / 座位闪烁定时器；若存在「本次调整」待提交记录，toast 提示已清空（与新建 / 切换方案同款保护，不静默丢弃教师的未归档调整）；
- **撤销**（只复用既有 store API）：`switchPlan(原方案)` → `removePlan(自动排座方案)`；`switchPlan` 对「目标不存在」与「已是当前」都返回 `false`，故以切换后的当前方案 id 判定结果，不把 `false` 当失败；撤销 / 换排法入口在「方案已不是当前 / 方案被编辑过（`updatedAt` 变化）/ 原方案已不存在」时**自动隐藏**（保守：宁可少给入口，也不误删教师后续的改动）；
- 「生成方案」与「换一种排法」每次都递增种子（同一输入下重复生成也得到不同排法）。

## 11. 开发规范（Phase 3 起必须遵守）

### 11.1 代码

- **TypeScript strict**：全程类型安全；业务类型集中在 `src/types/`（按领域分文件：`index.ts`（UI + 学生等）、`classroom.ts`、`seat.ts`、`constraint.ts`、`timetable.ts`、`dashboard.ts`），禁止组件内散落重复类型。
- **Vue 3 Composition API**：`<script setup lang="ts">` + typed props（`withDefaults`）/ typed emits；组件间通过事件通信，禁止跨层 prop 钻透。
- **组件职责**：通用交互进 `components/ui/`（已验收组件不改视觉）；页面局部组织在 `views/<Module>/components/`；页面只做编排，业务规则进 store。
- **职责边界**：`utils/` 纯函数（展示/格式化/类型守卫，可被任意层引用）；`services/` 未来数据访问抽象；`stores/` 领域状态 + 持久化 + 数据层校验；业务逻辑不进 utils、不走组件的全局单例。
- **Pinia 使用规范**：setup-style；`ref` + deep `watch` 持久化；**数组一律不可变更新**；只有"会被多个页面/组件共享"的数据进 store。
- **注释**：中文注释解释"为什么"，不复述代码；注释必须与实现同步（发现脱节只修注释不改行为，除非另有指示）。
- **导入约定**：组件统一从 `@/components/ui`（index.ts）导入；路径别名 `@` → `src`。

### 11.2 UI

- 主题变量一律取自 `theme.css`（禁止硬编码颜色/圆角/间距）；新 token 先补 theme.css 再使用。
- 交互范式沿用现有验收样式：按钮 variant、Modal 确认流程、Toast 反馈、空态 EmptyState、Badge 语义色。
- 列表/卡片在桌面网格中保持不拥挤；中文文案 + 全角标点；空值占位「—」。
- 响应式底线：表单窄屏单列（≤560px media 已有先例）；不随意改变已验收 UI。

### 11.3 数据

- Student 写入必须经由 `studentStore`（add/update/remove），**不允许组件直接 push/修改 `students.value` 绕过 Store**；localStorage 键名必须以 `appConfig.storageKeyPrefix` 拼接。
- schema 演进一律走「load 时 normalize + 默认值回退」，不引入迁移框架；升级不得覆盖旧数据、不得让旧数据崩溃。
- 新字段保持向后兼容：历史数据缺失 → `undefined`/`''`，展示层给占位，不臆造默认业务值。
- 空值边界：`familyLocation` 缺失保留 `undefined`（不构造"假位置"）；scope 非法回退需在注释说明假设依据。

### 11.4 开发流程（每个 Phase / 每次改动）

```
需求确认（与用户对齐，不擅自扩大范围）
↓
实现（小步增量；不改已验收稳定代码与 UI）
↓
自检（覆盖边界：空数据 / 旧数据 / 重名 / 重复学号）
